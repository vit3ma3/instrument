# Разбор проекта понятным языком

Этот файл помогает понять проект, а не просто выучить технические термины.
Сначала разберём общий путь данных, потом папки и файлы, а затем главные
функции. Если какой-то термин непонятен, в конце есть короткий словарь.

## 1. Что делает программа одним предложением

Программа получает файл с настройками на учебном языке, проверяет его,
подставляет константы и записывает те же настройки в виде XML.

Например, входной файл:

```text
var ports = {80, 443}
$[ports: @(ports)]
```

После разбора внутри Python получается обычный словарь:

```python
{"ports": [80, 443]}
```

А на выходе получается XML:

```xml
<?xml version="1.0" encoding="utf-8"?>
<config>
  <dictionary>
    <entry name="ports">
      <array>
        <number>80</number>
        <number>443</number>
      </array>
    </entry>
  </dictionary>
</config>
```

Здесь важно увидеть: **мы не выполняем настройки и не запускаем сервер**. Мы
только переводим описание настроек из одного формата в другой.

## 2. Как выглядит весь путь программы

Допустим, мы выполнили:

```bash
./run.sh -i examples/webserver.cfg -o output.xml
```

Дальше происходит следующее:

```text
run.sh
  ↓ запускает Python
__main__.py
  ↓ вызывает main()
cli.py
  ↓ читает входной файл
parser.py
  ↓ проверяет текст и создаёт int/list/dict
serializer.py
  ↓ создаёт XML-строку
cli.py
  ↓ записывает output.xml
```

То есть у проекта есть три главные рабочие части:

1. **`cli.py`** — общается с пользователем и файлами.
2. **`parser.py`** — понимает учебный язык.
3. **`serializer.py`** — переводит готовые значения в XML.

Остальные файлы помогают этим трём частям: запускают программу, содержат ошибки,
настройки, примеры или тесты.

### `src/`

Здесь находится сама программа. Название `src` — сокращение от source, то есть
«исходный код». Внутри лежит пакет `config_converter`.

Разделение на `src` и `tests` нужно, чтобы не смешивать программу с её

Здесь находятся небольшие программы, которые сами запускают наши функции и
проверяют результат. Например, передают строку `"{1, 2}"` и проверяют, что
получился список `[1, 2]`.

### `examples/`

Здесь лежат входные файлы, которые можно сразу передать программе. Их не нужно
создавать перед демонстрацией.

## 4. Файлы в корне проекта

### `run.sh`: кнопка запуска

Это небольшой shell-скрипт. Он нужен, чтобы не писать каждый раз длинную
команду и не думать, где находится папка `src`.

Скрипт делает три полезные вещи:

1. Находит папку проекта.
2. Если есть `.venv/bin/python`, использует Python из виртуального окружения.
   Если нет — использует `python3` или значение переменной `PYTHON`.
3. Запускает `python -m config_converter` и передаёт ему все наши аргументы.

Поэтому эти две команды по смыслу одинаковы:

```bash
./run.sh -i examples/webserver.cfg -o output.xml
```

```bash
PYTHONPATH=src python -m config_converter \
  -i examples/webserver.cfg -o output.xml
```

Первая просто короче и удобнее.

### `pyproject.toml`: паспорт проекта

В этом файле записано:

- проект называется `edu-config-xml`;
- нужен Python 3.10 или новее;
- для работы нужна библиотека `lark`;
- для разработки дополнительно нужны `build` и `ruff`;
- исходники следует искать в `src`;
- команда `config2xml` должна вызывать `config_converter.cli:main`;
- Ruff должен проверять код с длиной строки до 80 символов.

Благодаря этому файлу проект можно установить командой:

```bash
python -m pip install -e ".[dev]"
```

Здесь `-e` означает editable-установку: изменения в исходниках сразу видны
установленному пакету, переустанавливать его после каждой правки не нужно.

### `README.md`: инструкция для пользователя

Здесь описаны установка, запуск, правила языка, вид XML, функции и тесты.
`README.md` отвечает на вопрос «как пользоваться проектом», а текущий файл —
на вопрос «как проект устроен внутри».

### `.gitignore`: список ненужных для Git файлов

Например, туда входят `.venv`, `__pycache__`, `dist`, `build` и PDF. Эти файлы
могут существовать локально, но не попадают в репозиторий.

## 6. `__main__.py`: вход через `python -m`

Файл очень маленький. Его основная строка:

```python
raise SystemExit(main())
```

Когда мы пишем:

```bash
python -m config_converter
```

Python ищет внутри пакета именно `__main__.py`. Этот файл вызывает `main()` из
`cli.py`.

`SystemExit` завершает процесс с тем кодом, который вернула `main()`:

- `0` — всё получилось;
- `1` — произошла ошибка обработки;
- `2` — пользователь неправильно передал аргументы.

В этом файле нет логики разбора или XML. Он только запускает программу.

## 7. `cli.py`: командная строка и работа с файлами

CLI расшифровывается как Command Line Interface, то есть интерфейс командной
строки. Этот файл связывает пользователя с остальными частями программы.

В нём три функции.

### `build_argument_parser()`

Эта функция описывает, какие аргументы разрешено передавать:

```text
-i или --input   путь к входному файлу
-o или --output  путь к выходному файлу
-h или --help    справка
```

Оба основных аргумента обязательны. `type=Path` превращает полученную строку в
объект `pathlib.Path`, с которым удобно работать как с путём.

Если пользователь забыл `--input`, эту ошибку обрабатывает сам `argparse` и
показывает подсказку.

### `convert_file(input_path, output_path)`

Её логику можно показать четырьмя строками:

```python
source = input_path.read_text(encoding="utf-8")
value = parse_config(source)
output_path.parent.mkdir(parents=True, exist_ok=True)
output_path.write_text(to_xml(value), encoding="utf-8")
```

Построчно:

1. Прочитать исходный текст в кодировке UTF-8.
2. Вызвать `parse_config` и получить `int`, `list` или `dict`.
3. Создать папку для результата, если её ещё нет.
4. Вызвать `to_xml` и записать готовую строку.

Важен порядок: сначала полностью разбираем текст, только потом создаём выходной
файл. Поэтому при синтаксической ошибке новый XML не появляется.

### `main(argv=None)`

Это управляющая функция CLI. Она:

1. Получает аргументы.
2. Вызывает `convert_file`.
3. Если всё хорошо, возвращает `0`.
4. Если произошла ожидаемая ошибка, печатает её в `stderr` и возвращает `1`.

Перехватываются три группы ошибок:

- `ConfigError` — ошибки нашего языка;
- `OSError` — например, файл не найден или нет прав на запись;
- `UnicodeError` — проблемы с кодировкой текста.

Мы не прячем любые возможные ошибки под одно общее сообщение. Непредвиденная
ошибка программы останется видимой разработчику.

## 8. `parser.py`: самая важная часть

Этот файл отвечает на два вопроса:

1. Правильно ли записан входной текст?
2. Как превратить его в значения Python?

Для этого в файле есть четыре связанные вещи:

- тип `ConfigValue`;
- грамматика `GRAMMAR`;
- класс `ConfigTransformer`;
- функция `parse_config`.

### 8.1. Тип `ConfigValue`

Упрощённо его определение выглядит так:

```python
ConfigValue = int | list["ConfigValue"] | dict[str, "ConfigValue"]
```

Это подсказка типов, а не новый класс. Она говорит, что значением может быть:

- целое число;
- список других `ConfigValue`;
- словарь, где ключи — строки, а значения — снова `ConfigValue`.

Слово «рекурсивный» здесь означает только то, что определение ссылается само на
себя. Это нужно для вложенности:

```python
[1, [2, {"value": 3}]]
```

В одном списке одновременно могут находиться число, другой список и словарь.

### 8.2. Зачем нужна грамматика

Грамматика — это формальное описание того, что считается правильным текстом.
Мы передаём её библиотеке Lark.

Вместо ручного алгоритма «прочитай символ, проверь следующий, заведи стек» мы
записываем понятные правила:

```text
start: const_decl* value
const_decl: "var" NAME "=" value
?value: number | array | dictionary | const_ref
number: NUMBER
array: "{" (value ("," value)*)? "}"
dictionary: "$[" (entry ("," entry)*)? "]"
entry: NAME ":" value
const_ref: "@(" NAME ")"
NUMBER: /\d+/
NAME: /[a-z]+/
```

Разберём каждое правило на примере.

#### `NUMBER: /\d+/`

Число состоит из одной или нескольких цифр. Поэтому `42` подходит, а `-42` —
нет.

#### `NAME: /[a-z]+/`

Имя состоит из маленьких латинских букв. Например, `ports` подходит, а `Ports`
или `port1` — нет.

#### `const_decl`

Это объявление константы:

```text
var timeout = 30
```

`const_decl` расшифровывается как constant declaration — объявление константы.

#### `const_ref`

Это использование константы:

```text
@(timeout)
```

`const_ref` — сокращение от constant reference, то есть ссылка на константу.

#### `entry`

Это одна пара в словаре:

```text
timeout: 30
```

Слева имя, справа значение.

#### `array`

Массив начинается с `{`, заканчивается `}`. Внутри находятся значения через
запятую. Повторение необязательно, поэтому `{}` тоже разрешено.

Запись `{1,}` не подходит: после запятой правило ожидает ещё одно значение.

#### `dictionary`

Словарь начинается с `$[`, заканчивается `]`. Внутри находятся `entry` через
запятую. Пустой `$[]` тоже разрешён.

#### `value`

Значением может быть число, массив, словарь или ссылка на константу. Именно это
правило позволяет вкладывать конструкции друг в друга, потому что внутри массива
и словаря снова используется `value`.

#### `start`

Весь файл состоит из любого количества объявлений и одного итогового значения.

Подходят, например:

```text
42
```

```text
var answer = 42
@(answer)
```

А пустой файл не подходит, потому что в нём нет итогового значения.

### Обозначения в грамматике

- `|` означает «или»;
- `*` означает «повторять ноль или больше раз»;
- `?` после группы означает «группа необязательна»;
- `?value` — специальная подсказка Lark не создавать лишнюю обёртку вокруг
  выбранного варианта значения.

Строки `%import common.WS` и `%ignore WS` подключают стандартное определение
пробелов и говорят игнорировать их между частями языка.

### 8.3. Что делает Lark с грамматикой

Анализатор создаётся так:

```python
_PARSER = Lark(GRAMMAR, parser="lalr", lexer="contextual")
```

Lark читает входной текст и строит **дерево разбора**. Это не двоичное дерево и
не структура данных, которую мы пишем вручную. Это просто представление текста
в виде вложенных частей.

Для строки:

```text
$[values: {1, 2}]
```

упрощённо получается такая картина:

```text
start
└── dictionary
    └── entry
        ├── NAME "values"
        └── array
            ├── number 1
            └── number 2
```

Теперь видно не только какие токены были в тексте, но и где они находятся.

Параметр `parser="lalr"` выбирает тип синтаксического анализатора. Для защиты
достаточно сказать, что это эффективный стандартный алгоритм Lark, который
подходит нашей однозначной грамматике. `lexer="contextual"` помогает выбирать
допустимые токены с учётом текущего места в грамматике.

### 8.4. Зачем нужен `ConfigTransformer`

Дерево разбора ещё не является удобным результатом. Нам нужен не узел `number`,
а Python-число; не узел `array`, а Python-список.

`ConfigTransformer` проходит по дереву и заменяет его части готовыми значениями.
Можно представить его как сборщик: сначала он собирает внутренние детали, затем
передаёт их наружному узлу.

У класса есть словарь:

```python
self._constants = {}
```

В нём хранятся уже объявленные константы. Например, после `var timeout = 30`:

```python
{"timeout": 30}
```

Теперь разберём методы.

#### `number`

```python
return int(items[0])
```

Берёт токен вроде `"42"` и превращает его в число `42`.

#### `array`

```python
return list(items)
```

К моменту вызова элементы массива уже обработаны. Метод просто собирает их в
список. Например, числа `1` и `2` становятся `[1, 2]`.

#### `entry`

Возвращает пару:

```python
("ports", [80, 443])
```

Это ещё не целый словарь, а одна будущая запись в нём.

#### `dictionary`

Получает список таких пар и собирает из них Python-словарь. Перед добавлением
проверяет, не было ли уже такого имени:

```python
if name in result:
    raise DuplicateKeyError(name)
```

Без проверки второй одинаковый ключ молча заменил бы первый, и часть настроек
потерялась бы.

#### `const_decl`

Получает имя и уже вычисленное значение. Сначала проверяет, не было ли такого
имени раньше, затем сохраняет его:

```python
self._constants[name] = value
```

Метод ничего не добавляет в итоговую конфигурацию. Объявление нужно только для
вычислений.

#### `const_ref`

Ищет имя в `_constants`:

```python
if name not in self._constants:
    raise UnknownConstantError(name)
return self._constants[name]
```

Поэтому `@(timeout)` заменяется на ранее сохранённое значение.

Если константа ещё не объявлена, будет ошибка. Мы сознательно используем
последовательное правило: сначала объявление, потом использование.

#### `start`

Возвращает последний элемент списка обработанных частей. Последний элемент —
это итоговое значение файла. Объявления перед ним в результат не попадают.

### 8.5. Функция `parse_config`

Это главная функция файла. Снаружи достаточно вызвать только её:

```python
value = parse_config("var x = 1 @(x)")
```

Внутри она делает два шага:

```python
tree = _PARSER.parse(text)
result = ConfigTransformer().transform(tree)
```

Первый шаг проверяет синтаксис и строит дерево. Второй создаёт значения и
вычисляет константы.

Новый `ConfigTransformer` создаётся при каждом вызове. Значит, константы из
прошлого файла не сохраняются и не влияют на следующий файл.

### 8.6. Как обрабатываются ошибки Lark

Если текст не соответствует грамматике, Lark выбрасывает `UnexpectedInput`.
Мы превращаем его в собственный `ConfigSyntaxError` и сохраняем:

- строку;
- столбец;
- список того, что Lark ожидал увидеть.

Это нужно, чтобы остальному коду не приходилось зависеть от внутреннего формата
ошибок Lark.

Есть второй нюанс: если наша ошибка возникла внутри `ConfigTransformer`, Lark
оборачивает её в `VisitError`. Например, там может находиться наш
`UnknownConstantError`.

`parse_config` достаёт исходную ошибку из обёртки. Поэтому пользователь видит:

```text
Константа 'timeout' не объявлена перед использованием.
```

А не длинное внутреннее сообщение библиотеки.

## 9. `serializer.py`: из Python-значений в XML

После `parser.py` у нас уже есть примерно такой объект:

```python
{"ports": [80, 443]}
```

Теперь его нужно превратить в XML. Этим занимаются две функции.

### `to_xml(value)`

Это внешняя функция, которую вызывает CLI. Она:

1. Создаёт корневой элемент `<config>`.
2. Передаёт значение в `_value_to_element`.
3. Добавляет полученный элемент внутрь `<config>`.
4. Добавляет красивые отступы с помощью `indent`.
5. Возвращает строку с XML-декларацией и переводом строки в конце.

### `_value_to_element(value)`

Это внутренняя функция, о чём говорит подчёркивание в начале имени. Она смотрит
на тип значения.

#### Если получила `int`

Создаёт:

```xml
<number>42</number>
```

#### Если получила `list`

Создаёт `<array>`, затем для каждого элемента снова вызывает
`_value_to_element`.

Например, для `[1, 2]` получится:

```xml
<array>
  <number>1</number>
  <number>2</number>
</array>
```

#### Если получила `dict`

Создаёт `<dictionary>`. Для каждой пары «ключ — значение» создаёт `entry`, где
ключ записывается в атрибут `name`, а значение снова обрабатывается через
`_value_to_element`.

### Почему здесь нужна рекурсия

Рекурсия — это вызов функцией самой себя. Она удобна, потому что заранее
неизвестна глубина вложенности.

Для такого значения:

```python
{"items": [1, {"inner": [2]}]}
```

функция примерно так спускается внутрь:

```text
словарь
  → массив items
    → число 1
    → словарь
      → массив inner
        → число 2
```

На каждом уровне работает одно и то же правило. Не нужно писать отдельный код
для второго, третьего или десятого уровня вложенности.

Если функции передать неподдерживаемый тип, например строку, она выбросит
`TypeError`. При обычном разборе это не происходит, потому что parser создаёт
только разрешённые типы.

## 10. `errors.py`: свои понятные ошибки

Все ошибки конфигурации наследуются от `ConfigError`:

```text
ConfigError
├── ConfigSyntaxError
├── UnknownConstantError
├── DuplicateConstantError
└── DuplicateKeyError
```

Зачем нужен общий `ConfigError`? В CLI можно написать один перехват и поймать
все ожидаемые ошибки нашего языка.

Зачем тогда нужны отдельные классы? Они формируют разные понятные сообщения и
хранят полезные данные.

- `ConfigSyntaxError` хранит строку, столбец и ожидаемые токены.
- `UnknownConstantError` хранит имя неизвестной константы.
- `DuplicateConstantError` хранит имя повторной константы.
- `DuplicateKeyError` хранит повторный ключ словаря.

### Разница между синтаксической и семантической ошибкой

Синтаксическая ошибка — текст записан не по грамматике:

```text
{1, 2
```

Не хватает `}`.

Семантическая ошибка — по форме текст правильный, но его смысл недопустим:

```text
$[value: 1, value: 2]
```

Скобки и запятая расставлены правильно, но один ключ повторяется.

## 11. `__init__.py`: внешняя дверь пакета

Этот файл выполняется, когда кто-то импортирует пакет `config_converter`.

В нём мы выбираем, что считать удобным публичным интерфейсом:

```python
from config_converter.parser import ConfigValue, parse_config
from config_converter.serializer import to_xml
```

Поэтому можно писать:

```python
from config_converter import parse_config, to_xml
```

А не вспоминать каждый раз полные пути к файлам. В `__init__.py` почти нет
логики; он в основном собирает и экспортирует нужные имена.

## 13. Файлы тестов

Тесты разделены по тем же частям, что и программа. Это облегчает поиск нужной
проверки.

### `tests/test_parser.py`

Содержит 17 тестов. Проверяет:

- числа;

- обычные и пустые словари;
- вложенные конструкции;

## 14. Полный пример на маленькой конфигурации

Возьмём вход:

```text
var timeout = 30
$[server: $[timeout: @(timeout), ports: {80, 443}]]
```

Пройдём его по функциям.

### В `cli.py`

`convert_file` читает этот текст и передаёт его в `parse_config`.

### В `parser.py`

Lark видит:

- одно объявление константы;
- итоговый словарь;
- внутри него ещё один словарь;
- ссылку на константу;
- массив из двух чисел.

`ConfigTransformer`:

1. Сохраняет `timeout = 30`.
2. Превращает `{80, 443}` в `[80, 443]`.
3. Заменяет `@(timeout)` на `30`.
4. Собирает внутренний и внешний словари.

Результат:

```python
{"server": {"timeout": 30, "ports": [80, 443]}}
```

### В `serializer.py`

Внешний словарь становится `<dictionary>`. Ключ `server` становится
`<entry name="server">`. Внутри появляются записи `timeout` и `ports`, а массив
портов становится `<array>` с двумя `<number>`.

### Снова в `cli.py`

Полученная XML-строка записывается в файл, указанный через `--output`.

Это и есть весь проект: никакой скрытой дополнительной стадии между этими
шагами нет.

## 15. Что показать на защите

Удобный порядок демонстрации:

1. Открыть `examples/webserver.cfg`.
2. Показать объявления `requesttimeout` и `webports`.
3. Показать места, где используются `@(requesttimeout)` и `@(webports)`.
4. Запустить:

   ```bash
   ./run.sh -i examples/webserver.cfg -o output.xml
   ```

5. Открыть `output.xml` и найти готовые числа вместо ссылок.
6. Запустить тесты:

   ```bash
   python -m unittest discover -s tests -v
   ```

7. При желании показать ошибку на файле:

   ```text
   $[server: $[ports: {8080,}]]
   ```

После запятой нет значения, поэтому Lark сообщит синтаксическую ошибку, а XML
не будет создан.

## 16. Словарь терминов простыми словами

**Парсер** — часть программы, которая читает текст по правилам и определяет его
структуру. У нас парсер строится библиотекой Lark.

**Грамматика** — правила, по которым можно отличить правильную запись от
неправильной.

**Токен** — отдельная распознанная часть текста: число, имя, скобка или запятая.

**Дерево разбора** — представление текста в виде вложенных частей.

**Transformer** — объект Lark, который превращает узлы дерева в удобные нам
значения. У нас это `int`, `list` и `dict`.

**Семантика** — смысл уже синтаксически правильной записи. Например, разрешено
ли использовать это имя константы.

**Сериализация** — превращение внутреннего объекта в формат, который можно
сохранить. У нас это превращение `int/list/dict` в XML-строку.

**Рекурсия** — повторное применение того же правила или функции к вложенной
части. Например, обработка массива внутри словаря внутри другого массива.

**CLI** — способ управления программой командами и аргументами в терминале.

**Entry point** — точка входа, функция, с которой начинается пользовательский
запуск. У консольной команды это `config_converter.cli:main`.

**Виртуальное окружение** — отдельная папка с Python-зависимостями проекта,
чтобы они не смешивались с другими проектами. У нас это `.venv`.

**Wheel и sdist** — стандартные формы сборки Python-пакета. Их создаёт команда
`python -m build`; для обычной демонстрации транслятора они не нужны.

**Ruff** — инструмент, который проверяет оформление и типичные проблемы в коде,
но не заменяет тесты.

## 17. Быстрые ответы «где это находится?»

**Где правила языка?**  
В `GRAMMAR` внутри `src/config_converter/parser.py`.

**Где текст превращается в `int/list/dict`?**  
В `ConfigTransformer` там же.

**Где подставляются константы?**  
В `const_decl` и `const_ref`.

**Где создаётся XML?**  
В `to_xml` и `_value_to_element` в `serializer.py`.

**Где читаются и записываются файлы?**  
В `convert_file` в `cli.py`.

**Где обрабатываются аргументы?**  
В `build_argument_parser` в `cli.py`.

**Где формируются сообщения об ошибках?**  
В классах из `errors.py`.

**Где начинается запуск через `python -m`?**  
В `__main__.py`.

**Где находятся готовые демонстрации?**  
В `examples/`.

**Где проверяется правильность?**  
В четырёх файлах внутри `tests/`.

## 18. Понятный рассказ для защиты

> Программа состоит из трёх основных частей. Сначала `cli.py` получает пути к
> файлам и читает исходный текст. Затем `parser.py` с помощью Lark проверяет
> текст по грамматике и строит дерево разбора. `ConfigTransformer` превращает
> это дерево в обычные значения Python: числа, списки и словари. Во время этого
> прохода он сохраняет константы и подставляет их по имени. После разбора
> `serializer.py` рекурсивно превращает полученные значения в XML. Рекурсия
> нужна потому, что массивы и словари могут быть вложены друг в друга. В конце
> `cli.py` записывает XML в файл. Ошибки разбора и ошибки констант переводятся в
> собственные понятные исключения. Правильность отдельных частей и полного
> преобразования проверяется 31 тестом, а два готовых примера показывают работу
> на конфигурациях веб-сервера и библиотеки.
